## 1. Contexto e Objetivo

- **O que é:** Módulo de banco de perguntas reutilizáveis tipadas e de montagem de questionários por composição, com reordenação e status, base para agendamento (v0.4) e envio.
- **Por que existe:** Evitar duplicação de perguntas recorrentes (adesão, sintomas, peso, sono...), permitir comparação longitudinal e reduzir retrabalho ao montar novos questionários — DR-003.
- **Quem usa:** Nutricionista autenticada (perfil único). Paciente não acessa neste ciclo.
- **Escopo (dentro):** CRUD de perguntas com tipos `texto_livre, multipla_escolha, escala, numerico, sim_nao`; seed de perguntas padrão; CRUD de questionários com título/descrição/status; vínculo `QuestionarioPergunta` com `ordem`; reordenação persistida; bloqueio de exclusão de perguntas `padrao=true`; lista de questionários com filtro por status.
- **Fora de escopo:** Envio/agendamento (v0.4), respostas, versionamento profundo de pergunta já respondida (adota soft delete + aviso; bloqueio edição se já vinculada a questionário com envios futuros será tratado em v0.4), expiração de link (DR-005).

## 3. História de Usuário

```gherkin
Como nutricionista autenticada,
quero cadastrar perguntas tipadas e montar questionários selecionando e reordenando essas perguntas,
para que eu possa reaproveitar perguntas e enviar questionários consistentes sem redigitar.
```

**Cenários alternativos:**
- Não autenticada em `/questionarios` → 401 no API, redirect para `/login`.
- Criar pergunta sem título ou sem opções de múltipla escolha → erro inline + 400 com `details`.
- Tentar excluir pergunta padrão → 403 com mensagem informativa, não exclui.
- Editar pergunta já vinculada a questionário ativo → permitido neste ciclo, com aviso que histórico futuro deve versionar (DR-003 pendente p/ v0.4+).
- Questionário sem perguntas → erro "Selecione ao menos 1 pergunta".
- Reordenar por botões subir/descer → ordem persistida imediatamente via PUT; refresh reflete mesma ordem.
- Lista vazia de perguntas/questionários → EmptyState com CTA.

## 4. Requisitos Funcionais

- [ ] **RF-14:** O sistema permite criar pergunta com `titulo`, `tipoResposta`, e campos específicos por tipo: `multipla_escolha` exige `opcoesResposta` ≥2 itens não vazios; `escala` exige `escalaMin`/`escalaMax` com `min < max` e intervalo 1..10; `texto_livre/numerico/sim_nao` ignoram esses campos.
- [ ] **RF-15:** O sistema garante seed de 8 perguntas padrão (`padrao=true`) na primeira leitura quando coleção vazia: adesão às orientações, dificuldades encontradas, sintomas, peso atual, nível de energia, qualidade do sono, evacuação, prática de atividade física.
- [ ] **RF-16:** A nutricionista lista perguntas com busca por título e filtro por tipo; edita qualquer pergunta não-padrão; edição atualiza `updatedAt`.
- [ ] **RF-17:** A nutricionista cria questionário com `titulo` (2..120), `descricao` opcional, `status` (rascunho/ativo/inativo) e `perguntaIds` ordenados; o sistema persiste `QuestionarioPergunta` com `ordem` sequencial.
- [ ] **RF-18:** A nutricionista reordena perguntas dentro do questionário (subir/descer) e a ordem é persistida e retornada em `GET /api/questionarios/:id` com `perguntas` já ordenadas.
- [ ] **RF-19:** Questionário pode ser salvo como `rascunho` e depois publicado para `ativo`; `inativo` oculta de seleções futuras mas preserva histórico.
- [ ] **RF-20:** Perguntas com `padrao=true` não podem ser excluídas (DELETE retorna 403); soft delete padrão (`deletedAt`) vale para perguntas customizadas e questionários.

## 5. Requisitos Não-Funcionais

- **Performance:** Listagem p95 <600ms com até 500 perguntas / 200 questionários (O(n) em JSON); paginação `page/pageSize` até 50.
- **Segurança:** Todas as rotas `/api/perguntas*` e `/api/questionarios*` exigem `getAuth` + isolamento `nutricionistaId`; seed padrão cria perguntas por nutricionista na primeira requisição; `padrao` não pode ser setado via POST (ignorado, sempre `false` exceto seed); validação Zod estrita.
- **Acessibilidade:** Labels `htmlFor`, erros `role=alert` + `aria-describedby`, Dialog focus trap, botões reordenação com `aria-label`, tabs e listagens navegáveis por teclado, área toque ≥44px.
- **Compatibilidade:** últimas 2 versões Chrome/Edge/Firefox/Safari; mobile Safari/Chrome.
- **Observabilidade:** `console.error("[perguntas] / [questionarios]")` em catch; 400 retorna `details` flatten; sem log de dados sensíveis.
- **Persistência:** JSON file-based: `src/data/perguntas.json`, `src/data/questionarios.json`, `src/data/questionario_perguntas.json`; sem migrations.

## 6. Análise da Aplicação

- **Arquitetura:** Next.js 15 App Router + API Routes + JSON file store (`readCollection/writeCollection`) + JWT cookie (`getAuth`). Frontend client components com `fetch` + RHF+Zod. Sidebar já aponta para `/questionarios`.
- **Padrões:** `PascalCase` componentes, `camelCase` helpers, Tailwind+`cn`, shadcn/ui + Radix, `zodResolver`, `src/types` central, soft delete via `deletedAt`.
- **Fluxo de dados perguntas:** `GET /api/perguntas?q=&tipo=&page=` → `getAuth` → `readCollection<Pergunta>` filtra `nutricionistaId+!deletedAt` + busca `titulo contains` + `tipoResposta` → ordena `createdAt desc` → paginado. Seed roda quando coleção vazia para o nutricionista.
- **Fluxo questionários:** `POST /api/questionarios {titulo, descricao, status, perguntaIds[]}` valida Zod + verifica cada `perguntaId` pertence à nutricionista e não deletada → cria `Questionario` + N `QuestionarioPergunta` com `ordem`. `GET /api/questionarios/:id` junta perguntas ordenadas. `PUT` reescreve vínculos com nova ordem.
- **Contratos:** seguem `src/app/api/pacientes/**` → `{data}` ou `{error, details}` com 200/201/400/401/403/404.

## 8. Problemas e Impedimentos

### 8.1 Problemas Técnicos

- File-based sem transação: write de questionário + N vínculos não é atômico — mitigado por writes síncronos sequenciais e baixo volume; aceito até v0.6.
- Reordenação via drag-and-drop exigiria lib extra (`@dnd-kit`) — optado por botões Subir/Descer (acessível, sem dependência, RNF 5.1 satisfeito).
- Validação cruzada tipo↔campos (ex.: escala sem min/max) precisa de `superRefine` no Zod — coberto em `perguntaSchema`.
- `padrao` não pode ser injetado pelo cliente: backend ignora `padrao` do body e força `false` em POST/PUT.

### 8.2 Ambiguidades nos Requisitos

- Escala sempre 1..5 ou configurável? Plano diz min/max configuráveis; implementa `escalaMin/Max` 1..10, default 1-5, validado `min < max`.
- Múltipla escolha: quantas opções? Mínimo 2, máximo 20, strings 1..120 chars, trim + dedup.
- Numérico `sim_nao` vs `texto_livre` etc. — preview usa controles adequados mas sem persistir resposta (só visual).
- Versionamento DR-003: editar pergunta já usada deve versionar ou bloquear? Neste ciclo permite editar com aviso; bloqueio real entra quando houver envios (v0.4) — não bloqueante.

### 8.3 Riscos

- Regressão em auth: novo `getAuth` em 4 rotas — testar 401 sem cookie e 404 cross-nutricionista.
- Seed duplicada se 2 requisições concorrentes no primeiro acesso — `read`+`write` não atômico; risco baixo com single user; seed checa `exists` antes de escrever.
- Builder com muitas perguntas (100+) pode ficar lento em `GET /api/perguntas` sem paginação — paginação 20 no banco de seleção mitiga.

## 9. Critérios de Aceite

- [ ] **CA-09 (escala):** Dado pergunta `tipoResposta=escala escalaMin=1 escalaMax=5`, quando preview no builder, então 5 radio buttons 1..5 são renderizados com `aria-label` e seleção funciona.
- [ ] **CA-10 (multipla_escolha):** Dado pergunta `tipoResposta=multipla_escolha opcoes=["Op A","Op B","Op C"]`, quando preview, então 3 `radio` com label correspondente são exibidos.
- [ ] **CA-11 (reordenação):** Dado questionário com 5 perguntas, quando nutricionista clica "Subir" na pergunta 4 e salva (PUT), então `GET /api/questionarios/:id` retorna ordem persistida `[1,2,4,3,5]` e builder reflete.
- [ ] **CA-12 (padrão não excluível):** Dado pergunta `padrao=true`, quando `DELETE /api/perguntas/:id`, então 403 `{error: "Perguntas padrão não podem ser excluídas"}` e `GET` ainda a retorna.
- [ ] **CA-13 (RF-15 seed):** Dado nutricionista sem perguntas, quando primeiro `GET /api/perguntas`, então 8 perguntas padrão são criadas e retornadas; segundo GET não duplica.
- [ ] **CA-14 (criação pergunta texto_livre):** Dado `POST /api/perguntas {titulo:"Como se sente?", tipoResposta:"texto_livre"}`, quando sucesso, então 201 com `id` e listagem contém a nova pergunta.
- [ ] **CA-15 (questionário rascunho→ativo):** Dado `POST` com `status=rascunho` e depois `PUT status=ativo`, quando listado com `?status=ativo`, então questionário aparece; com `?status=rascunho` não aparece.
- [ ] **CA-16 (validação multipla_escolha):** Dado `POST` multipla_escolha sem `opcoesResposta`, quando enviado, então 400 com `details` em `opcoesResposta`.
- [ ] **CA-17 (responsividade 375px):** Dado viewport 375px no builder, quando 10 perguntas no banco, então sem scroll horizontal, seleção em coluna única, botões ≥44px.
- [ ] **CA-18 (segurança):** Dado `GET /api/perguntas` sem cookie, então 401; dado tentativa de usar `perguntaId` de outra nutricionista em `POST /api/questionarios`, então 404.

## 13. DDR — Design Decision Record

### DDR-012 — Seed lazy de perguntas padrão por nutricionista (em vez de migration/seed global)

**Status:** Aceito
**Contexto:** 8 perguntas padrão precisam existir para cada nutricionista sem exigir script manual. File-based não tem migration.
**Decisão:** Na primeira `GET /api/perguntas` do nutricionista, se `readCollection` filtrada por `nutricionistaId` estiver vazia, criar 8 registros `padrao=true` com `crypto.randomUUID()` e `writeCollection`.
**Alternativas:** Script `npm run seed` manual — descartado por fricção; seed global única — descartada por quebrar isolamento por nutricionista (DR-002).
**Consequências:** + zero setup, isolamento garantido; - concorrência no primeiro GET pode duplicar (mitigado, baixo risco single user).

### DDR-013 — Reordenação por botões Subir/Descer (em vez de drag-and-drop)

**Status:** Aceito
**Contexto:** Reordenar perguntas no questionário precisa ser acessível e sem dependência pesada.
**Decisão:** Botões `↑ Subir`/`↓ Descer` que trocam `ordem` no array e persistem via `PUT` com nova `perguntaIds` ordenada.
**Alternativas:** DnD com `@dnd-kit` — prós: UX arrastar; contras: +bundle, complexidade a11y (keyboard sortable), overengineering para MVP.
**Consequências:** + a11y nativa, sem deps, simples; - menos "fluido" que drag, aceito para MVP.

### DDR-014 — Validação cruzada por tipo via `superRefine` (single schema)

**Status:** Aceito
**Contexto:** Campos obrigatórios variam por `tipoResposta`; schemas separados fragmentariam validação.
**Decisão:** `perguntaSchema` único com `z.object` base + `.superRefine` que exige `opcoesResposta` para `multipla_escolha` e `escalaMin/Max` para `escala`.
**Alternativas:** Discriminated union `z.discriminatedUnion("tipoResposta", [...])` — mais verboso, duplicaria `titulo/obrigatoria`.
**Consequências:** + DRY, mensagem de erro por campo clara; - superRefine menos declarativo que union, mas mantido simples.
