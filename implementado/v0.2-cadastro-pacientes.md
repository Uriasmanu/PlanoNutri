## 1. Contexto e Objetivo

- **O que é:** Módulo de cadastro e gerenciamento de pacientes para a nutricionista: listagem com busca/filtros, formulário completo de cadastro/edição, perfil com abas, histórico de evolução física com gráfico, e exclusão com soft delete.
- **Por que existe:** Centralizar dados clínicos e antropométricos hoje dispersos em planilhas/WhatsApp, permitindo acompanhamento longitudinal da evolução física — núcleo do Job-to-be-Done do requisito 2.1.
- **Quem usa:** Nutricionista autenticada (perfil único — DR-002). Paciente não acessa o sistema.
- **Escopo (dentro):** CRUD completo de paciente, listagem com busca por nome + filtro por status + paginação, validação de campos obrigatórios, status ativo/inativo/em_pausa, registro e visualização de evolução física (peso, % gordura, cintura/quadril/braço), gráfico de peso, soft delete com confirmação.
- **Fora de escopo desta entrega:** Questionários/envios (v0.3+), histórico de respostas, canal de envio, criptografia em repouso de campos sensíveis (DR-008 será tratada com soft delete + controle de acesso nesta versão; criptografia real entra em v0.6 se houver store externo), gráfico de IMC/circunferências além de peso.

## 3. História de Usuário

```gherkin
Como nutricionista autenticada,
quero cadastrar, buscar, editar e acompanhar a evolução física dos meus pacientes,
para que eu tenha uma base única e histórica dos dados clínicos e possa orientar o acompanhamento.
```

**Cenários alternativos:**
- Usuária não autenticada tenta acessar `/pacientes` → redireciona para `/login` (401 no API).
- Cadastro com campo obrigatório vazio ou formato inválido → erro inline no campo, sem submit.
- Lista vazia (sem pacientes) → estado vazio com CTA "Cadastrar paciente".
- Paciente inativo/pausado → não aparece na listagem padrão, mas aparece com filtro correspondente.
- Exclusão → modal de confirmação; cancelamento não altera dados.
- Evolução: adicionar medição com data futura → erro de validação; peso negativo → erro.

## 4. Requisitos Funcionais

- [ ] **RF-06:** O sistema exibe lista de pacientes da nutricionista logada com busca por nome (contains, case-insensitive) e filtro por status (ativo/inativo/em_pausa/todos) e paginação (10 por página).
- [ ] **RF-07:** A nutricionista cadastra paciente com todos os campos obrigatórios validados (nome, dataNascimento, sexo, telefone, email, pesoInicial, altura, objetivo, nivelAtividadeFisica, status) e opcionais persistidos quando informados.
- [ ] **RF-08:** O sistema valida campos antes de salvar ( zod no backend + react-hook-form no frontend) e retorna 400 com detalhes por campo quando inválido.
- [ ] **RF-09:** A nutricionista edita qualquer dado de paciente existente (exceto id/nutricionistaId) e o sistema atualiza `updatedAt`.
- [ ] **RF-10:** A exclusão requer confirmação em Dialog e executa soft delete (`deletedAt = now`, status permanece) — paciente some das consultas normais; exclusão física não existe.
- [ ] **RF-11:** O sistema registra evolução física por paciente (dataAvaliacao, peso, medidas opcionais, observações) vinculada a `pacienteId` e ordenada por data.
- [ ] **RF-12:** O sistema exibe gráfico de evolução de peso (linha) ao longo do tempo para o paciente selecionado; tooltip com data + peso; vazio quando <2 pontos mostra mensagem.
- [ ] **RF-13:** Pacientes com `deletedAt != null` ou filtrados como inativo não aparecem na listagem padrão (`status=ativo` por padrão); filtro explícito traz cada status.

## 5. Requisitos Não-Funcionais

- **Performance:** Listagem p95 < 800ms com até 500 pacientes (file JSON); paginação server-side via query params; sem N+1.
- **Segurança:** Todas as rotas `/api/pacientes*` exigem cookie `accessToken` válido; isolamento por `nutricionistaId` (usuária só vê seus pacientes); validação Zod estrita; LGPD: soft delete obrigatório — `DELETE` nunca remove fisicamente.
- **Acessibilidade (WCAG 2.1 AA):** Labels associados (`htmlFor`), erros via `aria-describedby`/`role=alert`, Dialog com focus trap (Radix), área de toque ≥44x44, contraste 4.5:1, navegação por teclado, tabs com `role=tablist`.
- **Compatibilidade:** Chrome/Edge/Firefox/Safari últimas 2 versões; mobile Safari/Chrome.
- **Observabilidade:** Logs de API em `console.error` com contexto (rota, nutricionistaId, pacienteId); erros exibidos via toast/Alert; sem log de dados sensíveis.
- **Persistência:** Reuso de `src/lib/db.ts` (coleções `pacientes.json`, `evolucao_fisica.json` em `src/data/`). Sem migration SQL nesta fase (file-based é decisão de v0.1).

## 6. Análise da Aplicação

- **Arquitetura geral:** Next.js 15 App Router (React 19) + API Routes (`src/app/api/*`) + file-based JSON store (`src/lib/db.ts`) + JWT em cookie httpOnly (`src/lib/auth.ts` com `jose`). Frontend client components com `useAuth` context; layout com `Sidebar`.
- **Padrões em uso:** `PascalCase` componentes, `camelCase` funções, Tailwind + `cn()`, Zod + React Hook Form (dependências já instaladas), shadcn/ui via Radix, `src/types/index.ts` centraliza domínios.
- **Fluxo de dados:** `fetch /api/pacientes` (com cookie) → `verifyToken` → `readCollection("pacientes")` filtrando `nutricionistaId` + `deletedAt==null` → JSON → componente lista → estado local + paginação. Evolução: `POST /api/pacientes/:id/evolucao` valida paciente pertence à nutricionista e não está soft-deletado.
- **Contratos de API existentes:** `POST /api/auth/login` → `{ user, accessToken, refreshToken }`, `GET /api/auth/me` → 401 sem cookie. Novo contrato segue mesmo padrão: `Authorization` via cookie, status `200/201/400/401/404`, body `{ data }` ou `{ error, details }`.

## 8. Problemas e Impedimentos

### 8.1 Problemas Técnicos

- Store file-based (`src/data/*.json`) não é transacional; concorrência de writes pode perder update — mitigado por writes síncronos (`fs.writeFileSync`) e baixo volume do MVP (uso single-nutricionista). Risco aceito até v0.6 decidir por SQLite/Postgres.
- Validação de unicidade de e-mail do paciente não tem índice — varredura O(n) aceitável até ~1k pacientes; não bloquear.
- Recharts não está em `package.json` — será instalado como dependência nova (única adição).
- `Dialog`/`Select`/`Textarea` podem estar ausentes em `src/components/ui/` — serão criados via padrão shadcn local (sem CLI).

### 8.2 Ambiguidades nos Requisitos

- Telefone: formato livre BR ` (XX) XXXXX-XXXX` validado por regex leniente — não bloquear DDD inválido nesta versão.
- Peso/altura: `pesoInicial` 20..500 kg, `altura` 0.5..2.5 m — limites clínicos razoáveis para evitar erro de digitação.
- Data de nascimento: não pode ser futura nem idade >120 anos.
- Histórico clínico/restrições: `string` livre, pode ser vazio; não exigido mas persistido como "".
- Canal/envio não aparecem aqui — perfil tem aba "Questionários" como placeholder (v0.4+).

### 8.3 Riscos

- Regressão em auth: tocar em `verifyToken` em novas rotas pode expor bug de expiração — mitigado com helper `getAuthOr401(request)` centralizado.
- Inconsistência de padrão file-based vs. futuro Postgres — manter `nutricionistaId` desde já (DR-002) evita retrabalho.
- Gráfico com 1 ponto: Recharts `LineChart` precisa tratar array <2 — exibir empty state em vez de linha quebrada.

## 13. DDR — Design Decision Record

### DDR-009 — Persistência file-based JSON para v0.2 (adiamento de Postgres)

**Status:** Aceito

**Contexto:** v0.1 escolheu `src/lib/db.ts` com `src/data/*.json` (fs sync) sem Prisma/Postgres para validar produto rapidamente. v0.2 precisa de duas novas entidades (paciente, evolução). Migrar para Postgres agora atrasaria o MVP e exigiria infra (Docker, migrations).

**Decisão:** Manter file-based JSON para `pacientes` e `evolucao_fisica`; adiar Postgres para v0.6 ou quando >1k pacientes / necessidade de transações. Manter `nutricionistaId` e `deletedAt` para futura migração sem retrabalho.

**Alternativas consideradas:**
- **Postgres + Prisma agora:** Prós — transacional, query rica; Contras — setup, migrations, hospedagem, curva de aprendizado alta para prazo do MVP.
- **SQLite + better-sqlite3:** Prós — file único transacional; Contras — ainda exige migration e driver nativo (problemas em Vercel).

**Consequências:**
- Positivas: entrega mais rápida, código já padronizado, sem dependência externa.
- Negativas: sem transações reais, risco de race em writes concorrentes; queries O(n); limites de escala.

### DDR-010 — Gráfico de evolução com Recharts (em vez de Chart.js)

**Status:** Aceito

**Contexto:** Necessidade de gráfico de linha de peso leve, responsivo, acessível, integrado ao tema CSS variables.

**Decisão:** Usar `recharts` (declarativo, React puro, ResponsiveContainer, Tooltip customizável) — já previsto no Design System §13.

**Alternativas:**
- **Chart.js + react-chartjs-2:** Prós — mais plugins; Contras — imperativo, canvas, peso maior, tema menos integrado ao Tailwind.
- **Visx/D3:** Prós — controle total; Contras — complexidade excessiva para caso simples.

**Consequências:**
- Positivas: API declarativa, fácil customização de cores (`hsl(var(--primary))`), bom suporte a TS.
- Negativas: dependência adicional (~50kb gz); se performance degradar, troca por solução mais leve.

### DDR-011 — Validação compartilhada Zod (single source of truth)

**Status:** Aceito

**Contexto:** Validação duplicada (Zod no backend + RHF no frontend) tende a divergir.

**Decisão:** Centralizar schemas em `src/lib/validations/paciente.ts` e importar tanto nas API routes quanto no `PatientForm` via `zodResolver`. Backend sempre revalida mesmo se frontend já validou.

**Consequências:**
- Positivas: consistência, DRY, fácil teste unitário dos schemas.
- Negativas: schemas ficam acoplados a mensagens em pt-BR; se precisar de i18n, extrair.
